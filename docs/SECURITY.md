# Security and trust boundaries

## Threat model

Codex is capable but not trusted to define its own scope or success. A malformed or
incorrect task may attempt to modify inputs, control files, unrelated outputs, file
permissions, or symbolic links; it may also claim tests passed without evidence.

## Controls

- Codex runs only in disposable task copies.
- The subprocess receives a minimal explicit environment; ambient API keys, tokens,
  passwords, user Codex configuration, history, and MCP configuration are not inherited.
- Workspace-write network access is disabled unless the user explicitly enables asset
  sourcing.
- Input files reject symlinks, traversal, device files, oversize files, filename
  collisions, and unsafe names; materialized inputs are read-only.
- The mutation guard snapshots protected content, audits content and mode changes,
  rejects symlinks, verifies required outputs, and rolls back violations.
- Canonical promotion occurs only after physical validation.
- HTML rejects remote resources, active URL schemes, forms, embeds, meta refresh, and
  inline event handlers.
- SVG and Mermaid assets reject active content and external references.
- Browser evidence is generated by Python with external requests blocked and bound to
  the current HTML and screenshots by SHA-256.
- QA uses independent audit, repair, and verification contexts.

## Secrets

Use environment variables or the deployment secret manager. Do not place credentials
in prompts, workspaces, committed configuration, traces, or test fixtures. Sensitive
trace payloads are disabled by default.
